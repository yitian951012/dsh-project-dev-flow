# 不可外推边界的写法

> 用途：案例最大的风险是被当成通用规则引用。边界段就是防这一手的。

## 边界的三个维度

| 维度 | 要写什么 | 例子形态 |
| :--- | :--- | :--- |
| 前提 | 这套做法依赖的硬前提 | 「前提是判据可执行；判据不可观察时做法失效」 |
| 规模 | 在什么量级内成立 | 「按项目实测，超出该量级需重新评估成本」 |
| 权限 | 依赖谁的授权 | 「前提是决策人可当场签认；无签认渠道时退化为草案」 |

## 好边界 vs 坏边界

| 坏写法 | 问题 | 改法 |
| :--- | :--- | :--- |
| 视情况而定 | 等于没写 | 列出具体的「情况」是什么 |
| 一般适用 | 过度外推 | 写明不适用场景 |
| 我们的做法就是标准 | 单项目取舍当规则 | 改为「在 P 项目的约束下成立」 |
| 只要认真执行就没问题 | 掩盖条件缺失 | 写出依赖的前提是否可满足 |

## 边界与方法的衔接

- 方法文档里允许出现该案例的「提炼结论」，但不得出现该案例的数字与过程。
- 方法引用案例时用「见 case:<id> 的边界段」，不复制边界原文。
- 边界过期（前提不再成立）时，案例保持不动，改方法里的引用并标「前提已变」。

## 自查四问

1. 换一个完全不同约束的项目照做，会不会明显受伤？（会 → 边界没写全）
2. 边界里是否至少有一条是「权限/授权」类，而不只是技术前提？
3. 是否存在「只要…就…」的绝对句？（有 → 改成带前提）
4. 边界能否被一条命令或一份登记复核？（不能 → 写得太抽象）
