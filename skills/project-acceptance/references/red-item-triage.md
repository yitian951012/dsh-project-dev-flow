# 红项处置

> 用途：验收出红后，最容易发生的错误是「让红灯变绿」而不是「让实现正确」。

## 先分类，再动手

| 红因 | 判定线索 | 允许动作 | 禁止动作 |
| :--- | :--- | :--- | :--- |
| 实现错 | 判据合理，输出不符 | 改实现，复跑同一命令 | 改判据迁就实现 |
| 判据错 | 判据与已登记决策冲突，或断言本身不成立 | 回受理单修判据，登记变更 | 直接删断言 |
| 用例错 | 用例前置状态或期望值写错 | 修用例，写明为什么要改 | 放宽断言掩盖行为变化 |
| 环境错 | 缺依赖、缺配置、端口占用等 | 记录环境事实，重跑或标未验证 | 把环境失败写成实现失败 |
| 偶发 | 重跑结果不稳定 | 重复执行并记录次数与差异 | 只取通过的那一次当结论 |

## 处置顺序

1. 记录红项：判据编号、命令原文、exit code、关键输出行、最小复现步骤。
2. 按上表判定红因，写出证据支持该判定，而不是写「估计是」。
3. 若是实现错：修实现，复跑同一命令，同 commit 重取证据。
4. 若是判据或用例错：先登记再改，改后必须重跑整套，防止掩盖其他红。
5. 剩余的不修项写成残余问题：影响面、触发条件、谁决定不修。

## 升级条件

- 红因涉及契约、数据、守卫变化 → 必须先登记决策，不允许 agent 自行裁定。
- 同一判据连续多次反复红 → 判据本身可能不可观察，回受理单重写。
- 无法在本 commit 修复 → 输出「候选完成 + 具体红项 + 剩余风险」，不得说「基本完成」。

## 自查

- 本次改动是否同时动了判据、用例、守卫？若是，逐条说明理由，无理由即回滚。
- 修完之后，同一命令是否在改动后的实现上重新跑过？
