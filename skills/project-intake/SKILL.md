# 需求受理

## 何时使用

- 用户描述了一个目标、缺陷或改动，但没说清验收标准。
- 已有任务在实现中提出「顺带也改一下」，需要判断是否纳入本批。
- 需要把模糊反馈转成可执行判据，或需要判断是否该先登记决策。

## 输入

- 用户原话与原始材料；已有 {{doc:index}}、{{doc:decision-log}}、{{doc:status}}。
- 项目 profile（验证、测试、端到端命令；未配置即「未验证」）。
- 相关约束：撞车风险、依赖、不可动区域（禁用操作）。

## 步骤

1. 先加载 `../../methods/intake-and-decision.md`；判据写法与受理单字段见 `references/intake-checklist.md`。
2. 原文复述需求，并把「用户说的」与「我推断的」分成两栏；推断项逐条标「待确认」。
3. 归类：新能力、契约或数据变化、缺陷、纯文档四类之一。
4. 命中「新能力 / 契约或数据变化 / 判据变化」→ 先登记 {{doc:decision-log}} 并标 {{role:approver}}；未登记不进实现。
5. 写受理单：字段以 `references/intake-checklist.md` 的九项必填为准（该表即表单，不另设模板），逐项填并在输出里标「缺项」。
6. 判据必须落到可执行命令（{{command:verify}} / {{command:test}} / {{command:e2e}}）或可观察事实；两者都做不到时写「人工判据 + 判定人」。
7. 拆最小可交付批次：一个批次只解决一条判据，批次间可独立验证。
8. 范围外的一律写入不做清单与待裁决项，不在本批内暗中扩；归口与互斥规则见 `../../methods/truth-and-lifecycle.md`，处置流程见 `references/scope-guard.md`。
9. 有「待确认」项时只输出提问清单并停下，不自行补全需求。

## 输出

- 受理单：按 `references/intake-checklist.md` 九项逐项填写（目标、非目标、逐条判据、判据归属、证据口径、影响面、风险与依赖、批次拆分、决策需求）。
- 决策需求清单（谁签认、要登记哪条）。
- 待确认问题清单，逐条写明「不确认会导致什么」。
- 明确结论：受理 / 部分受理 / 不受理，并给出理由。

- 决策与待裁决项落成 [决策记录卡](../../templates/decision-record.md) / [待裁决项](../../templates/open-item.md)。

## 停止条件

- 判据可执行或可观察，且 {{role:approver}} 已确认（或用户明确「先做最小批次」）。
- 存在「待确认」项且无法当场确认 → 停在提问，不进入实现。
- 需求命中禁用操作或需数据变更 → 停在人工授权。

## 常见错误

- 把推断写成需求，后面所有判据都建在推断上。
- 判据写成「体验良好」「性能可接受」这类不可判定表述。
- 只记做什么，不记不做什么，实现中自然蔓延。
- 拿模板判据或别项目判据当本项目判据。
- 先改代码，事后再补决策登记。
