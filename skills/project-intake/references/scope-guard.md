# 范围护栏

> 用途：受理时最容易犯的错不是漏需求，而是把「顺带」当成本批范围。

## 四类去向

| 提出的东西 | 去向 | 处理 |
| :--- | :--- | :--- |
| 直接支撑当前判据 | 本批 | 写进受理单判据与影响面 |
| 同一根因的连带修复 | 本批（须声明） | 在受理单加一行「连带」并列出判据 |
| 改善但不是当前判据所需 | 不做清单 | 登记理由与触发条件，不在本批实现 |
| 需要决策、数据变更或跨主体 | 待裁决 | 写明缺什么决策、谁裁决 |

## 最小批次的三条线

1. 一个批次只服务一组判据，判据之间可独立验证。
2. 批次内改动可回滚，且回滚方式在受理单里写清。
3. 批次完成后能产出可交付证据；不能产出的批次太大。

## 范围扩大的合法路径

1. 停止实现，回到受理：新增判据编号 → 影响面复核 → 是否需决策登记。
2. 若新范围改变契约或数据，先登记 {{doc:decision-log}}，再实现。
3. 明确告知本批延后，不让「顺手改」混进当前证据。

## 范围压缩的合法路径

- 判据不变、批次变小 → 允许，但要在受理单记录「本批只覆盖哪些判据编号」。
- 判据减少 → 需 {{role:approver}} 确认，不允许 agent 自行降低判据。

## 红旗（出现即停）

- 「先实现，判据后面再补」。
- 「这个改动很小，不用登记决策」。
- 「顺手把相关的地方都改一下」。
- 「验收时再说标准」。
