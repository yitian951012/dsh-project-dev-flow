# 案例：从 No-Go 到 GO 的一次全量验证

> 来源：来源项目（下称 P），2026-11 全量测试与复测两轮（脱敏，原文不随包发布）。
> 证据可获得性：unavailable（仅摘要；现场产物未随包发布，不可独立复核）。

## 1. 背景与约束

- 首轮做了白盒、端到端、接口黑盒与可访问性四类检查，结论是 No-Go。
- 阻断项集中在三类：默认网络暴露面、端到端不稳定、可访问性严重问题。
- 硬约束：交付形态是本地应用，不能靠「上线后打补丁」；修复不能改判据来消红。

## 2. 当时的错误判断

- **判断一：修完阻断项就能直接交付。** 实际上复测还需要证明「修复没有引入新问题」，且必须换到同一份新提交上重跑。
- **判断二：不稳定用例只要重跑通过就算过。** 实际做法是把不稳定用例单列，判定时不并入通过数；否则同等于是用重跑掩盖缺陷。
- **判断三：检查项全绿即可宣布完成。** 实际仍存在不能在本轮解决的残余风险，只能登记并指定接受人。
- 错在哪一步：把「本轮验证结论」当成了「项目终态结论」。

## 3. 候选方案与实际取舍

| 方案 | 当时评估 | 实际选择 | 事后看 |
| :--- | :--- | :---: | :--- |
| 带风险直接交付 | 最快 | 未选 | 阻断项属于用户可感知的安全与可用性问题 |
| 修完全部问题再复测 | 最干净 | 未选 | 部分问题超出本轮范围，强行修会扩大改动面 |
| 修阻断项 + 复测 + 登记残余风险 | 成本可控 | 选 | 结论可复核，风险有归属 |
| 只修阻断项不复测 | 省时 | 未选 | 无法证明修复本身没问题 |

取舍理由：放弃了「一次清零」，换取「结论可被第三方复核 + 风险显式化」。

## 4. 可观察证据

| 证据 | 形式 | 结果量级 | 位置 |
| :--- | :--- | :--- | :--- |
| 首轮结论 | 验证报告 | No-Go，阻断项分类列出 | 初测报告 |
| 修复范围 | 变更记录 | 仅针对阻断项与其直接关联 | 修复留痕 |
| 复测执行矩阵 | 报告表格 | 白盒、端到端、接口黑盒、一致性与可访问性逐层 | 复测报告 |
| 复测结论 | 验证报告 | GO，残余风险转入问题看板 | 复测报告与问题看板 |
| 端到端两轮 | 命令输出 | 两轮数量一致，无新增失败 | 复测报告 |

## 5. 修复后仍未解决的风险

| 风险 | 当时状态（截至案例时点） | 下一次的触发条件 |
| :--- | :--- | :--- |
| 可访问性仍存在未清零项 | 已登记，未修复 | 面向真实用户发布或做合规评估时 |
| 不稳定用例的根因未彻底消除 | 已单列，未根治 | 同一用例在下一轮再次出现不一致 |
| 清理与归档不完整 | 部分产物未纳入版本控制 | 需要第三方复现同一结论时 |
| 默认网络暴露面已收紧但未做渗透验证 | 配置层修复 | 暴露到共享网络环境前 |

## 6. 能提炼的方法与不可外推边界

| 可提炼 | 不可外推 |
| :--- | :--- |
| 结论必须绑定同一提交的证据；跨提交拼接无效 | 不适用于纯文档或纯设计评审——那类结论不依赖运行证据 |
| 不稳定用例不得计入通过数，必须单列并说明 | 不能据此认为「所有不稳定都应阻塞交付」；需按影响面判级 |
| 修复后再复测，是为了证明修复本身没有引入新问题 | 不是所有修复都需要全量复测；改动面小的可用定向证据 |
| 残余风险必须有接受人，否则等于无人负责 | 高风险项的「接受」不能由 agent 代办，必须由人类授权者承担 |
