# 案例：全绿但守不住的检查器

> 来源：来源项目（下称 P），2026-10 到 2026-11 的技术债与不变量守卫轮次（脱敏，原文不随包发布）。
> 证据可获得性：unavailable（仅摘要；守卫脚本与变异记录未随包发布，不可独立复核）。

## 1. 背景与约束

- 项目有多类自动检查：结构一致性、禁止字面量、迁移守卫、写入口守卫、不变量断言。
- 约束：检查器必须能在无人值守的门禁里运行；不能靠人肉复核所有规则。
- 现实：多次出现「检查器绿灯，但实际约束被绕过」与「检查器红灯，但内容其实合法」。

## 2. 当时的错误判断

- **判断一：脚本退出码为 0 就意味着规则有效。** 实际出现过的失败机制：只匹配文件里首次出现的位置、扫描集合为空时直接返回通过、白名单过期后仍然放行、匹配到注释里的示例文本。
- **判断二：规则写了就生效。** 实际有的规则从未被真实触发过，等于永远通过。
- **判断三：红灯就是要改内容。** 有时是规则本身写错（过宽或过窄），改内容只是掩盖规则缺陷。
- 错在哪一步：把「检查器」当成结果，而不是当成需要被验证的对象。

## 3. 候选方案与实际取舍

| 方案 | 当时评估 | 实际选择 | 事后看 |
| :--- | :--- | :---: | :--- |
| 逐条人工复核规则 | 最准 | 未选 | 不可持续，且无法防止未来回退 |
| 给每条规则加人工说明 | 成本低 | 未选 | 说明不会阻止规则失效 |
| 控制组 + 变异验证 + 过期失败 | 成本较高 | 选 | 能证明规则有判别力，且退化会显形 |
| 只保留少量强规则 | 最简单 | 未选 | 覆盖不足，缺口会转移到别处 |

取舍理由：放弃了「规则越多越好」的直觉，换取「每条保留下来的规则都被证明能失败」。

## 4. 可观察证据

| 证据 | 形式 | 结果量级 | 位置 |
| :--- | :--- | :--- | :--- |
| 守卫清单 | 表格：守什么、假绿风险点、验证方式 | 逐条可查 | 不变量守卫文档 |
| 变异验证记录 | 每次注入缺陷后的检查结果 | 注入后应失败；未失败即规则无效 | 技术债与守卫记录 |
| 假绿实例 | 案例：扫描集合为空、只校验首个匹配、注释被误判 | 多次 | 技术债计划与实测问题 |
| 浏览器实测发现 | 实测记录：门禁未覆盖的路径 | 与黑盒结论不一致处 | 实测问题清单 |

## 5. 修复后仍未解决的风险

| 风险 | 当时状态（截至案例时点） | 下一次的触发条件 |
| :--- | :--- | :--- |
| 变异验证不在常规门禁里 | 仍在：需单独执行 | 有人只跑常规门禁就宣称守卫有效 |
| 白名单与豁免有有效期但无人清理 | 部分缓解 | 到期日临近而无人复核 |
| 注释与示例文本仍可能被规则误伤 | 部分缓解 | 新增规则时未加负向样本 |
| 覆盖集中在浏览器来源 | 仍在 | 出现非浏览器客户端调用写入口 |

## 6. 能提炼的方法与不可外推边界

| 可提炼 | 不可外推 |
| :--- | :--- |
| 检查器必须被变异验证：注入一个确定违规的样本，必须失败；不失败即规则无效 | 不适用于每次都要跑；适合规则新增或修改时执行 |
| 扫描集合为空时要显式失败，而不是返回通过 | 不能推广成「所有空集合都报错」——空集合有时是合法初始态 |
| 白名单必须带到期日，过期自动失败 | 对稳定且不可能变化的技术常量不必要 |
| 「红灯」先分清是内容错还是规则错，再决定改哪边 | 不能据此允许改判据来让红灯变绿；判据变更必须登记 |
| 门禁覆盖是有限的，黑盒实测用于发现未覆盖路径 | 不能把黑盒实测当成可重复门禁的替代品 |
