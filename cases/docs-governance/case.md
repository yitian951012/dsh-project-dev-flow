# 案例：多套索引并存导致文档漂移

> 来源：来源项目（下称 P），2026-11 文档审计与治理轮（脱敏，原文不随包发布）。
> 证据可获得性：unavailable（仅摘要；原始审计记录未随包发布，不可独立复核）。

## 1. 背景与约束

- 文档数量随交付轮次增长，先后出现过四套并列索引：仓库根说明、状态看板、架构文档、系统架构各维护一份清单。
- 同时存在两套「历史文档」判定口径：一套是文档里的自述，一套是检查器里的文件名正则；两份正则的匹配面还不一样。
- 硬约束：已有文档不能删；审计报告必须保留被审文档的旧值以便追溯；检查器不能因此整体失效。

## 2. 当时的错误判断

- **判断一：检查器全绿就等于文档已自洽。** 实际是两条正则互相抵消：同一份文档在一条规则下被当作活、在另一条下被当作史，两边都不报，绿灯只证明「没抓到」。
- **判断二：四套索引各自维护没问题。** 实际是新增文档只被其中一两套收录，读者按不同入口会得到不同的「有哪些文档」。
- **判断三：合并文档会丢历史。** 实际的做法可以是原文整段保留、只换宿主并登记旧名到新名。
- 错在哪一步：把「格式检查通过」当成「治理口径统一」，属于典型的检查器假绿。

## 3. 候选方案与实际取舍

| 方案 | 当时评估 | 实际选择 | 事后看 |
| :--- | :--- | :---: | :--- |
| 只修索引，不动判定口径 | 工作量最小 | 未选 | 会继续留下两套判定，漂移复发 |
| 统一判定口径，但保留四套索引 | 风险中等 | 未选 | 索引仍是四处维护，迟早再分叉 |
| 建唯一索引 + 性质列 + 登记册 | 改动面最大 | 选 | 后续新增文档只需两件事，漂移显著减少 |
| 全量重写文档 | 最彻底 | 未选 | 成本不可接受且会丢时点信息 |

取舍理由：放弃了「一次把文档写干净」的彻底方案，换取「规则可执行、改动可回退」的收敛路径。

## 4. 可观察证据

| 证据 | 形式 | 结果量级 | 位置 |
| :--- | :--- | :--- | :--- |
| 并列索引清单 | 审计报告表格 | 四套入口，各自维护一份清单 | 审计报告 |
| 判定相反文档清单 | 逐行登记表 | 一批文档在两套正则下判定相反 | 生命周期登记册 |
| 收敛后的一致性检查 | 项目自带一致性检查脚本 | 退出码 0，且新增「索引性质」作为唯一豁免口径 | 检查器输出 |
| 合并登记 | 旧名到新宿主映射表 | 逐条可查，原文保留 | 登记册 |

## 5. 修复后仍未解决的风险

| 风险 | 当时状态（截至案例时点） | 下一次的触发条件 |
| :--- | :--- | :--- |
| 活文档内嵌历史附录 | 仍在：部分活文档带「时点原文、不回改」附录 | 附录里出现与当前规则冲突的旧值 |
| 索引与登记册双写 | 仍在：两处都要改 | 只改一处导致扫描面与登记不一致 |
| 审计报告需保留旧值 | 仍是例外：审计报告被强制纳入扫描 | 有人用它当现状引用 |

## 6. 能提炼的方法与不可外推边界

| 可提炼 | 不可外推 |
| :--- | :--- |
| 索引只做定位，数字必须回源；索引一旦抄数字就产生第二个事实源 | 不适用于只有几份文档的小项目——那时建索引的维护成本大于收益 |
| 性质（活 / 史 / 档）是判定开关，改性质等于改审查面，必须与登记同步 | 不能假设「只要标了性质就一定准确」；标注本身也需要复核 |
| 历史材料合并时原文保留、只换宿主，并登记旧名映射 | 不适用于需要独立引用粒度的材料，硬合并会让引用失效 |
| 检查器绿灯只证明「没抓到」，需要用变异样本验证判别力 | 变异验证成本较高，对一次性脚本不值得 |
